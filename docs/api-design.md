# QuickNotes API Design

## 1. Overview

QuickNotes provides a REST API for authenticated users to create,
read, update and delete their notes. The API exchanges JSON over
HTTPS and uses bearer-token authentication.

Base URL: `https://api.quicknotes.example/v1`

All note resources belong to the authenticated user unless the
endpoint explicitly describes another scope.

## 2. Endpoints

| Method | Path | Description | Success status |
|---|---|---|---|
| POST | /auth/register | Register a user | 201 Created |
| POST | /auth/login | Authenticate and obtain a token | 200 OK |
| GET | /notes | List the authenticated user's notes | 200 OK |
| GET | /notes/{id} | Retrieve one note | 200 OK |
| POST | /notes | Create a note | 201 Created |
| PATCH | /notes/{id} | Update some fields of a note | 200 OK |
| DELETE | /notes/{id} | Delete a note | 204 No Content |
| GET | /tags | List the user's tags | 200 OK |
| POST | /notes/{id}/tags/{tagId} | Associate a tag with a note | 204 No Content |

All endpoints except registration and login require a valid
bearer token. IDs are generated by the server.

## 3. List notes

### Request

`GET /v1/notes?page=1&limit=20`

Headers:

`Authorization: Bearer <access-token>`

Optional query parameters:
- `page`: page number, starting at 1.
- `limit`: number of notes per page, from 1 to 100.
- `q`: optional search text.

### Response: 200 OK

```json
{
  "data": [
    {
      "id": 42,
      "title": "Project ideas",
      "body": "Plan the next release.",
      "createdAt": "2026-10-01T10:00:00Z",
      "updatedAt": "2026-10-01T10:00:00Z",
      "tags": [
        {
          "id": 3,
          "name": "work"
        }
      ]
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 1,
    "totalPages": 1
  }
}


## Create a Note

### POST /notes

Creates a new note for the authenticated user.

**Authentication:** Required. The client must provide a valid access token.

**Request headers:**

```http
POST /notes HTTP/1.1
Content-Type: application/json
Authorization: Bearer <access_token>
```

**Request body:**

The `title` field is required and must contain between 1 and 100 characters after trimming whitespace. The `body` field is optional. The server determines the `userId` from the authenticated user's token rather than trusting a user ID supplied by the client.

```json
{
  "title": "Shopping list",
  "body": "Buy bread, milk, and eggs."
}
```

**Successful response: `201 Created`**

The server saves the note and returns the created resource.

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /notes/101
```

```json
{
  "data": {
    "id": 101,
    "userId": 1,
    "title": "Shopping list",
    "body": "Buy bread, milk, and eggs.",
    "createdAt": "2026-10-29T10:00:00Z",
    "updatedAt": "2026-10-29T10:00:00Z"
  }
}
```

The `id` is generated by the server. The timestamps are generated by the server and returned in ISO 8601 format. The `Location` header identifies the newly created note.

## Standard Error Responses

All API errors use a consistent JSON structure. This allows frontend clients to handle errors predictably without needing a different response format for every endpoint.

### Error response format

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid data.",
    "details": [
      {
        "field": "title",
        "message": "Title must contain between 1 and 100 characters."
      }
    ],
    "requestId": "req-abc123"
  }
}
```

Fields:

- `error.code`: A stable machine-readable error identifier.
- `error.message`: A human-readable explanation of the problem.
- `error.details`: Optional additional information, such as which field failed validation.
- `error.requestId`: A unique identifier that helps developers and support teams investigate a failed request.

The `details` field may be omitted when additional details are unnecessary. Error responses must not expose passwords, access tokens, database credentials, or internal stack traces.

### HTTP error status codes

| Status code | Meaning | When it is returned |
|---|---|---|
| 400 Bad Request | Invalid request | The JSON is malformed, a required field is missing, or input validation fails. |
| 401 Unauthorized | Authentication required or invalid | The access token is missing, invalid, or expired. |
| 403 Forbidden | Action not permitted | The user is authenticated but is not allowed to perform the requested action. |
| 404 Not Found | Resource not found | The requested note or endpoint does not exist. For notes the user cannot access, the API may also return 404 to avoid revealing another user's data. |
| 500 Internal Server Error | Unexpected server failure | An unexpected error occurs while processing the request. The response must not expose internal implementation details. |

### Example: 400 Bad Request

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request contains invalid data.",
    "details": [
      {
        "field": "title",
        "message": "Title is required and must not exceed 100 characters."
      }
    ],
    "requestId": "req-400001"
  }
}
```

### Example: 401 Unauthorized

```json
{
  "error": {
    "code": "UNAUTHENTICATED",
    "message": "A valid access token is required.",
    "requestId": "req-401001"
  }
}
```

### Example: 403 Forbidden

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "You are not permitted to perform this action.",
    "requestId": "req-403001"
  }
}
```

### Example: 404 Not Found

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "The requested resource was not found.",
    "requestId": "req-404001"
  }
}
```

### Example: 500 Internal Server Error

```json
{
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "An unexpected error occurred. Please try again later.",
    "requestId": "req-500001"
  }
}
```

## Frontend Error-Handling Expectations

The frontend should check the HTTP status code and parse the standard error response when possible.

- For `400`, show a useful validation message near the relevant form field.
- For `401`, ask the user to sign in again.
- For `403`, explain that the requested action is not permitted.
- For `404`, explain that the requested resource could not be found.
- For `500`, show a friendly message and allow the user to retry.

The frontend should not display raw server stack traces or sensitive internal information. The `requestId` can be included in support reports to help diagnose unexpected failures.
